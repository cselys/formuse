# V1.3 prospective validation safety (B1)

This is an orchestration remediation, not a new scoring strategy. V1.3 here is
the frozen H1+H4 overlay on the V1.2 baseline. The root `config` directory is
resolved from the source file, never the working directory. Scanner version
must be `1.2`. The separate `stock_scanner/config` scanner-version-1.3 contract
must not be substituted or mixed into this cohort. Both configurations remain
unchanged. Contract identity includes configuration/universe bytes, calculation
implementation, orchestration implementation and the frozen overlay.

## Production status

B1 authorizes implementation and isolated fixture tests only. It does not
authorize any production invocation, candidate calculation, outcome update,
HTML export or JSON commit. Existing records lacking the new contract evidence
are readable, but writing is blocked. Do not fill in their contract metadata
by assumption. A separately reviewed provenance plan is required.

2026-10-10 is a maintenance date, not a signal trading session. Neither 10-09
nor 10-08 is automatically substituted. Recovery remains blocked pending
10-09 input evidence and signal provenance. Historical reconstruction cannot
be labelled prospective; B1 does not implement retrospective import or backfill.

## Dates and offline inputs

`executed_at` is a timezone-aware execution timestamp. The CLI uses the real
clock and rejects a supplied timestamp more than one minute from it. The
Python candidate API accepts an injected clock for deterministic tests; it is
a trusted internal API, not an attestation or historical import endpoint.
Recording requires the explicitly selected trading session to be closed and
to match the New York execution date. Weekend/holiday decisions fail closed.

The decision close is propagated to `scan(as_of=...)` along with immutable
offline frame copies. The offline path disables AI and watchlist writes and
never calls refresh/download/cache-loading helpers. Frames must include every
configured symbol/benchmark, the exact target session, at least 252 daily
bars, and a continuous exchange-session history. There is no benchmark/date
fallback. Existing V1.2 weekly resampling and all scoring formulas are retained.

Outcome updates are independent of signal recording. `outcome_cutoff` must
be timezone-aware and no later than execution. Only completed NYSE sessions
are eligible, including early closes. The exact decision close and the
continuous +N-session interval must be present. Missing data blocks the whole
candidate, without partial persistence. Existing outcomes cannot be replaced.
Stored future outcomes relative to a requested cutoff block the update; they
are never deleted. Historical return, rounding and MFE/MAE definitions remain
unchanged; this change does not reinterpret those metrics.

## State consistency and no-op semantics

Session observations are immutable signal snapshots. The global observations
carry evolving outcomes. Their members and immutable fields must agree;
outcome fields need not be identical. Reloading JSON must not change behavior
through shared Python object identity.

An identical same-date signal set is a no-op. Changed scores, source dates,
members, duplicates or inconsistent session counters fail closed. Missing
members are not silently appended. Signal recording cannot update outcomes;
outcome updates cannot add signals. Old records are never auto-migrated.

## Modes

`--summary-only` reads the authoritative JSON, checks consistency and prints
metrics to stdout. It does not access price caches, instantiate a scanner,
create directories, update outcomes or save files. `--no-scan` is retired
because it previously concealed writes. Old implicit scan/save APIs now fail.

`--write-mode record` and `--write-mode outcomes` require an explicit expected
baseline SHA-256 and the appropriate dates. They create a candidate before
committing; operators can inspect `prepare_candidate` separately. Candidate
diffs include old/new values, input and calculation identity, timestamps,
operation, baseline hash and commit identity. They are not authorization tokens.

HTML is a separate explicit `--export-html` operation requiring the expected
JSON hash and a new destination. Existing reports cannot be overwritten. The
HTML includes its authoritative JSON SHA-256. No daily reports or watchlists
are generated by the validation workflow. HTML failure never retries a JSON
commit. No claim of a multi-file transaction is made.

## Persistence and recovery

The cumulative JSON is the single authority. Commit validates the candidate,
takes an exclusive sibling `.lock`, rechecks the baseline and transitions,
and rechecks input/configuration hashes. Immutable preimage and candidate
copies go into `<json-name>.audit/<sha256>.json`. A same-directory temporary
file is written, flushed, fsynced and read back before `os.replace`. Baseline
is checked again immediately before replacement. `metadata.last_commit`
contains the deterministic identity, predecessor hash and candidate diff.

Pre-replacement failures leave authoritative bytes unchanged. Audit files may
remain as evidence; no automatic retry repairs them. Lock contention stops.
Replacement/post-check uncertainty raises `CommitUncertain`. Use the read-only
`inspect_commit` comparison: `COMMITTED`, `NOT_COMMITTED`, or `UNKNOWN`.
Never retry automatically. A stale lock after a process crash needs a separate
operator review. All writers must obey the lock; old scripts must be stopped.
An uncooperative writer can still race the hash check. Atomic replacement is
not a guarantee of multi-file or power-loss durability on every filesystem.

## Tests and boundaries

Run tests only in a temporary source/config copy, without production output,
data or caches. Some pre-existing universe tests create a database relative
to their test file location; do not run those tests in the production checkout.
The new tests use synthetic completed-session OHLCV and temporary JSON paths.
Coverage includes date propagation, future cutoff, missing sessions/benchmarks,
same-date conflicts, snapshot consistency, read-only behavior, baseline drift,
lock contention, serialization/flush/fsync/replace failures, uncertain commits,
HTML provenance and exact equality with the existing V1.2 calculation pipeline.

The retired regression fixtures for implicit scan-and-report writes and
calendar-day outcomes were replaced with stricter lifecycle and exchange-session
tests. Frozen H1+H4 and existing metric tests are retained.
